# 阶段 9 笔记：订单域与「保单 / 订单」拆分

> 这一阶段的起点是一句吐槽：「这个投保流程好像只是个演示版本，没有实际的功能」。
> 按「问题 → 回答」记录：为什么像 demo、订单域怎么设计、三个幂等从哪来、
> 以及为什么最后把「我的订单」从「我的保单」里拆了出来。

---

## 一、为什么投保流程看起来像 demo

### 问题

> "这个投保流程好像只是一个演示版本，没有实际的功能。"

### 回答

不是"忘了写"，是**库里没有它能落脚的地方**。

| 流程步骤 | 实际发生了什么 |
|---|---|
| 保费试算 | 什么都没有（`rate_table_items` 是空表） |
| 客户告知 / 健康告知 | 什么都没有（`policies` 表里没有被保人字段） |
| 保单信息 | 什么都没有 |
| 确认支付 | 唯一真实的一步：PATCH → 方案项 insured + 插一条 policy |

也就是说，**点 5 次「下一步」等于什么都没做**，然后"支付"一下直接出单。

更尴尬的是：有数据的功能（产品列表、条款检索、方案生成）点起来像真的，
偏偏这个每一步都在空转的页面最像 demo。**中间状态最伤** —— 要么做实，要么砍掉。

### 为什么先做订单，而不是先做试算

- 试算需要费率数据，而费率表要从 PDF 里解析出来，是独立的"费率域"，按天算
- 订单不用改表结构：`orders` 表早就设计好了（订单号、金额、状态机、幂等键），一行代码没用过
- 订单是支付的真实对象 —— 有了它，"支付"才有金额、有单据号、有状态

## 二、订单域的接口

| 接口 | 说明 |
|---|---|
| `POST /api/v1/orders` | 从方案明细创建待支付订单，返回订单号 + 总保费 |
| `POST /api/v1/orders/{id}/pay` | 订单转已支付，同事务里标记方案项、发保单 |
| `GET /api/v1/orders` | 我的订单，按下单时间倒序，最多 20 条 |
| `GET /api/v1/orders/{id}` | 订单详情，别人的订单 404 |

状态机（`orders.status` 的 check 约束里定义了 5 个态）：

```
pending_payment ──pay()──> paid
      │                      
      └──(以后)──> cancelled

pending_policy / completed：留给"支付成功但保险公司还没回单"这类真实场景，本轮不用
```

## 三、为什么价格不让前端传

下单入参只有 `planId` + `itemIds`：

```json
{"planId": "...", "itemIds": ["...", "..."]}
```

产品、单价、总价全部从**方案明细**里读。原因很直接：
**前端能改的东西就是能被改的**。如果前端传 `total_premium: 1.00`，后端照单全收，
那订单表里的金额就没有意义了 —— 它只能证明"用户说他要付 1 块"。

顺带一个副作用：单价来自方案明细，而方案明细是 Python 在用户确认时落库的，
所以"这个价格从哪来"这条链路是可追的。

## 四、下单 ≠ 出单

```
下单：orders 插一行，pending_payment，不发保单
支付：orders → paid，同事务里 方案项 insured + 发保单
```

如果下单就发保单，那"未支付"的订单也会占一张保单，用户不付款就白白多一张；
而且重复下单会堆一堆垃圾保单。

分成两步之后：
- 订单可以一直挂着（未支付），不影响任何保单数据
- 取消订单（以后做）只需要改订单状态，不需要回收保单

## 五、三个幂等是怎么叠起来的

| 层 | 防的是什么 | 手段 |
|---|---|---|
| 下单 | 用户连点两次"下单"，多出两张单 | `idempotency_key = MD5(userId \| planId \| 排序后的 itemIds)`，加唯一索引 |
| 支付 | 用户连点两次"支付"，重复出单 | 已支付/已完成/待出单 → 直接返回；只有 `pending_payment` 才继续 |
| 保单 | 前两层被绕过时的最后一道 | 保单主键由方案项 id 派生（name-based UUID），同一项永远是同一张 |

第一层的细节：**明细先排序再拼**。否则"先选 A 再选 B"和"先选 B 再选 A"会算出两个键，
用户换个顺序点就多出一张订单。验收时专门把顺序反过来试过。

第二层的边界：`if (!"pending_payment".equals(status)) throw` ——
`cancelled` 的订单不能支付，但也**不能**被当成"已处理"直接返回，必须报错。

## 六、为什么订单项存 JSON，不建 order_items 表

`orders.items` 是一个 JSON 数组，元素形状：

```json
{
  "plan_id": "...", "plan_item_id": "...",
  "product_id": 1, "product_name": "达尔文宝贝计划12号",
  "premium": 285.30, "priority": 1
}
```

理由：

1. **订单项不会有自己的生命周期** —— 它不会被单独修改、单独查询、单独删除，
   永远是"跟着订单一起读出来的附属数据"
2. 避免一次关联查询（列表页 10 个订单 = 11 次查询 vs 1 次）
3. 里面存了 `product_name` 快照：产品以后改名，历史订单显示的仍是当时买的东西

代价：想按"买了某个产品的订单"做筛选会很难查。但当前没有这个需求。

## 七、支付为什么直接复用方案域

```java
for (OrderItem item : order.getItems()) {
    planService.markItemInsured(item.getPlanId(), item.getPlanItemId());
}
```

`markItemInsured` 已经做好了：明细标记、方案状态推进、发保单、幂等。
订单域只负责"这笔交易"，两者在同一个事务里（`@Transactional` 默认 REQUIRED 传播，
内层加入外层）。

如果另写一套"订单支付后的发单逻辑"，就会出现两份规则 ——
哪天方案项的投保规则改了，两边会不一致。**跨域调用比复制代码便宜。**

## 八、为什么最后把「我的订单」从「我的保单」里拆出来

### 问题

> "这个我的订单是在我的保单里面，要不要把这两个分开"

### 回答

要分开，因为它们是**两种对象**：

| | 保单 | 订单 |
|---|---|---|
| 是什么 | 长期契约，一年都在 | 一次购买行为，付完就结束 |
| 状态 | 保障中 / 已到期 / 已终止 | 待支付 / 已支付 / 已取消 |
| 后续操作 | 理赔、续保 | 取消、重新支付、看详情 |
| 生命周期 | 长 | 短 |

把订单塞在"我的保单"的 tab 里，名字就已经不对了。
而且**待支付**是唯一需要用户主动回来处理的状态，藏进 tab 很容易被忽略。

拆完之后：
- 导航变成 4 项：保险产品 / 服务保障 / 我的保单 / 我的订单
- 订单页标题直接提醒：`共 3 笔订单，1 笔待支付`
- 两页共用 `insuranceCards.tsx` 里的 `PolicyCard` / `OrderCard`，样式一套

## 十、这一轮**没做**的

1. **真实支付**：`pay()` 里直接认为钱到账了，留了 `TODO(支付)` —— 接真实渠道后要校验回调签名
2. **取消订单**：`cancelled` 状态没用上；取消后幂等键会阻挡重新下单，届时得处理
3. **订单详情页**：接口有 `GET /orders/{id}`，前端还没做页面
4. **待支付订单的"继续支付"入口**：现在只能重新走投保流程（会命中同一张待支付订单）
5. **保费试算**：仍然是"方案里的预算估计"，不是精算结果
