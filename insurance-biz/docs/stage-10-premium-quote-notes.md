## 一、为什么保险需要"试算"这种功能

### 问题

> "为什么会有试算这种功能？"

### 回答

因为**保险的价格不是一个数字，是一个函数**。

```
同一款百万医疗险
  30 岁 男 有社保 → ¥240
  30 岁 女 有社保 → ¥216
  30 岁 男 无社保 → ¥312
  55 岁 男 无社保 → ¥1,060
  保额从 200 万加到 400 万 → 再乘一个系数
```

价格是 `f(产品, 年龄, 性别, 保额, 社保, 职业, 缴费期...)`。离开这些参数，
产品页上根本写不出"多少钱"，只能写"¥136 起"，然后让用户填信息现算 —— 这就是试算。

它同时承担三件事：

1. **报价**：给用户一个能拿来做决定的数
2. **预核保**：年龄超限、职业高危在试算阶段就能拦掉
3. **留痕**：报过什么价、按什么参数算的，要能查（合规要求）

## 二、真实费率表是什么

### 问题

> "真实费率表是什么？"

### 回答

保险公司给每个产品出的**价目表**，精确到"什么年龄、什么性别、买多少保额、交几年，每年多少钱"。
精算结果，要报监管备案，一般是带签章的 PDF。

它和条款是两份文件、两个用途：

| 文档 | 回答什么 | 在本项目里 |
|---|---|---|
| 条款 | 保什么、不保什么、怎么赔 | ✅ 已解析进 Milvus，做 RAG |
| 费率表 | 多少钱 | ❌ 一张数据都没有 |

常见三种形态（对应 `rate_plans.rate_type` 的枚举）：

**① 年龄段 × 缴费期，单位"每千元保额"**（重疾、寿险）

| 投保年龄 | 10 年交 | 20 年交 | 终身交 |
|---|---|---|---|
| 26-30 | 2.4 | 3.5 | 4.7 |
| 31-35 | 3.1 | 4.6 | 6.2 |

表里是**费率**不是保费：每 1000 元保额的年价格。50 万保额 = 500 个千元单位，
20 年交 → `4.6 × 500 = 2300 元/年`。

**② 计划 × 年龄段，直接给保费**（医疗险）

| 计划 | 一般医疗保额 | 有社保 | 无社保 |
|---|---|---|---|
| 计划一 | 200 万 | 265 | 580 |

**③ 保额矩阵**：年龄 × 保额二维表，合并单元格最多，最难解析。

落库分三步，正好对应三张表：

```
rate_table_files  ← PDF 原件（哈希去重、解析状态、校验报告）
      ↓ 解析
rate_plans        ← 这个产品有哪几个"计划"
      ↓
rate_table_items  ← 一行行费率（年龄区间、性别、社保、缴费期、保额、费率值/保费）
```

`rate_table_items` 还有 `source_page` / `source_table` 两列 —— 设计者已经想到
"数据要能追溯回 PDF 第几页哪张表"。

### 为什么解析很难

合并单元格、多页续表、脚注改规则（"40 岁以上费率上浮 20%"）、
"每千元"和"每万元"混用、`0-5` / `0~5` / `0-4周岁` 各写各的、扫描件要 OCR，
解析完还得校验"同维度下保费单调递增"这类常识。这是一个独立的数据工程，按天算。

## 三、为什么先走 demo_formula

`premium_quotes.pricing_mode` 的枚举本来就是：

```
table 查费率表 / demo_formula 本地公式 / mock_adapter 模拟保司接口
/ insurer_api 真实保司接口 / local_fallback 兜底
```

**原设计就预留了"没有真实费率数据时用别的方式"**。所以这一轮走 `demo_formula`，
接口形状、表结构、前端表单都按最终形态做，只是数据源临时换成公式。

## 四、公式怎么设计

```
年保费 = 基准保费 × 保额系数 × 年龄系数 × 性别系数 × 社保系数
```

| 系数 | 取值 |
|---|---|
| 基准保费 | `products.min_premium`（空则 100） |
| 保额系数 | 保额 ÷ 险种参考保额，夹在 0.5 ~ 3.0 |
| 参考保额 | 医疗 300 万 / 重疾 50 万 / 寿险 100 万 / 意外 50 万 |
| 年龄系数 | 0-17: 0.60 / 18-25: 0.70 / 26-30: 0.85 / 31-35: 1.00 / 36-40: 1.25 / 41-45: 1.60 / 46-50: 2.00 / 51-55: 2.60 / 56-60: 3.40 / 61+: 4.50 |
| 性别系数 | 男 1.05 / 女 0.95 / 其他 1.00 |
| 社保系数 | 仅医疗险：无社保 1.30，有社保 1.00 |

两个算例：

```
重疾险 基准 3185，30 岁男，50 万保额
  3185 × 1.000 × 0.85 × 1.05 = ¥2842.61

医疗险 基准 255，35 岁女，80 万保额，无社保
  80 万 ÷ 300 万 = 0.267 → 夹到 0.50
  255 × 0.500 × 1.00 × 0.95 × 1.30 = ¥157.46
```

### 为什么要夹上下限

医疗险保额普遍是几百万，用户填 50 万时系数只有 0.167，保费会被压到接近零 ——
真实医疗险不是"保额按比例线性缩放"。所以限制在 0.5~3.0 倍。

### 踩过的坑：解释文案和算式对不上

第一版把"夹完之后"的系数直接拿去拼解释文案：

```
保额 ¥500000 ÷ 参考保额 ¥3000000 = 0.500     ← 算错了，实际是 0.167
```

用户拿计算器一按就发现不对。修法是先算原始值、再夹、分情况写文案：

```java
BigDecimal raw = coverage.divide(reference, 4, HALF_UP);
BigDecimal factor = raw.max(MIN).min(MAX);
if (factor.compareTo(raw) == 0) {
    explain.add("保额 … ÷ 参考保额 … = " + factor);
} else {
    explain.add("保额 … ÷ 参考保额 … = " + raw + "，按上下限取 " + factor);
}
```

**给用户看的每一句话，都必须能被他用计算器验证。**

## 五、六个实现上的决定

### 1. 存快照，不存"指针"

```java
quote.setRequestParams(paramsOf(dto));    // 当时填了什么
quote.setResult(resultOf(breakdown));     // 当时怎么算的
```

一年后公式改了，还能回答"这张保单当时的钱是怎么算出来的"。

### 2. `total_premium` 单独存一列

JSON 列没法排序、没法 SUM。要做价格统计或按价排序，必须有一列真正的数字。

### 3. `expires_at`：报价有保质期（24 小时）

保险价格会随费率调整变化，"昨天的价"不能用来卖"今天的保单"。

### 4. 表单由后端给，前端按 `fields` 渲染

```java
if ("medical".equals(product.getCategory())) { fields.add(社保字段); }
```

加字段、改默认值、改选项都不用动前端。这正是 `product_pricing_schemas` 存在的意义 ——
将来接入真实产品配置，只换数据源。

### 5. 纯函数 + 零依赖

`DemoFormulaPricing` 不碰 Spring、不碰数据库、没有状态：

```java
public static Breakdown calculate(Product product, PremiumQuoteDTO dto)
```

好处是能直接单测（不需要 mock），将来换成 `TablePricing`（查费率表）时，
调用方一行不用改。等它需要查库了，再交给容器管。

### 6. 金额一律 BigDecimal + HALF_UP，且只舍入一次

五次乘法只在最后 `setScale(2)` 一次。每步都舍入会累积误差，用户会发现"算出来差几毛"。

## 六、订单怎么引用试算结果

```
试算 → quote_id
        ↓
下单（带 quoteId）→ 校验：属于本人 / 未过期 / 产品一致 / 只买一项
        ↓
order.total_premium = quote.total_premium    ← 不再是方案里的预算估计
        ↓
orders.quote_ids = [quote_id]
```

四条规则：

| 规则 | 为什么 |
|---|---|
| 只能买一项 | 一次试算只对应一个产品，避免"一单里有的按试算、有的按预算" |
| 产品必须一致 | 防止拿 A 的报价买 B |
| 过期要重新试算 | 价格会变 |
| 幂等键加入 quoteId | 重新试算后价格变了，应该生成新订单，而不是被旧订单挡住 |

`orders.quote_ids` 这一列在初版表结构里就有（`JSON NOT NULL DEFAULT (JSON_ARRAY())`），
**一行 SQL 都没改**。

## 七、验收结果

| 项 | 结果 |
|---|---|
| 试算·重疾 | 3185 × 1.000 × 0.85 × 1.05 = **¥2842.61**，与手算一致 |
| 试算·医疗（无社保） | 255 × 0.500 × 1.00 × 0.95 × 1.30 = **¥157.46**，夹上下限的说明文案正确 |
| 表单 | 医疗险多出「是否有医保」，重疾险没有 |
| 越权 | 别人的 quote → 404 |
| 反例·产品不一致 | 400「试算报价与所选产品不一致」 |
| 反例·引用试算买多项 | 400「引用试算报价时，一次只能投保一个产品」 |
| 下单金额 | 157.46 = 试算价（**不再是方案预算 255**） |
| 重复下单 | 返回同一张订单 |
| 支付 | policy 生成，方案 applying（2 项投了 1 项） |

前端 `tsc --noEmit` 通过；浏览器人工点验：试算表单按字段渲染、改参数会清空旧报价、
最后一步显示试算价、支付后订单金额一致。

## 八、这一轮**没做**的

1. **真实费率表解析**：`rate_table_files` / `rate_plans` / `rate_table_items` 仍是空表
2. **核保**：健康告知、职业限制、体检 —— 真实流程里报价之后还有这一关，我们整段跳过
3. **保司接口对接**：`insurer_api_adapters` / `product_pricing_bindings` 没用上
4. **试算表单的真实配置**：`product_pricing_schemas` 是空表，字段是代码里写死的模板
5. **职业类别参与定价**：收进参数、存进快照，但不影响价格
